## 二、为什么重写（三条硬理由）

1. **原始设计已作废**：首版按"App 写 JSON + GitHub Actions 汇总"设计；现在数据源是 vault 的周计划 markdown —— 现有代码是在过时模型上打补丁。
2. **无完整心智模型**：4 个 AI 轮流改，各人只掌握自己那块；最近三次故障均源于此。
3. **产品定义已更新**：App = **执行终端**（今天做什么 → 打卡 → 复盘）。

**代价（不粉饰）**：需控股人**装机验证 3 轮**（唯一无法替代的环节）；真机行为（推送/计时/开机自启）要重新确认；旧 APK 保留可回滚。

## 三、不变量（红线）

①数据契约冻结（路径 / 文件名 / section 一字不改）②**只读不写**（App 永不写回 vault）③包名签名不变 ④缓存优先（离线可看今天）⑤失败必可解释 ⑥依赖不增加

## 五、控股人的功能想法 → 实现方案（2026-09-24 夜并入）

### 5.1 版本号（**我的疏漏，已定新规则**）
- **现状查明**：`pubspec` 一直是 `1.0.0+1` 从未递增；设置页的 "StudyPulse v1.0.0" 是**写死的字符串** → 所以你每次装都显示 1.0.0
- **新规则**：
  - `versionName` 随阶段走：**S1 = 1.2.0 · S2 = 1.3.0 · S3 = 1.4.0 · 重写完工 = 2.0.0**
  - `versionCode` **每次出包 +1**（Android 覆盖安装的依据）
  - 设置页显示**真实版本**（由构建脚本注入，不再写死）
  - APK 文件名带版本：`StudyPulse-1.2.0+2-首页骨架.apk`（一眼看出装的是哪版）
  - 构建脚本 `tool/release.sh`：读 pubspec → 生成版本常量 → 构建 → 复制到 `04-交付物/`；脚本自带一致性校验（防止版本又漂）

### 5.2 饼状图（专注时长分布）——**不困难，半天内**
- 数据**已经存在**：现有 `storage_service` 已按"日期→科目→分钟"记录（`getDailyMinutes` / `getWeekDailyTotals`）
- 实现：自绘 Donut（`CustomPainter`，**不加依赖**）+ 图例列表（科目 / 时长 h:mm / 百分比）
- 维度：**日 / 周 / 月** 三档切换（对应你图里的"日/周/月/自定义"，自定义先不做）
- 归属：**S2**（饼图是"记录"的视图，必须先有完整记录）

### 5.3 时间轴 + 学习记录 + 周总结——**能实现**
**数据模型**（本地 JSON，不写回 vault）：
```
Session {
  id · subject · startAt · endAt? · minutes · source(计时 / 任务打勾 / 手动补录)
  note(心得) · done · dateKey
}
```
- 一次"开始/结束学习" = 时间轴一行（时间段 / 科目 / 分钟 / 心得输入）
- **打勾完成任务**也写一条记录（`source=task`）→ 自动出现在时间轴
- 支持手动补录（忘了计时也能补）
- **周总结**：App 只负责出数据（本周各科时长、完成率、未完成项、心得），**总结由我写并落库**（避免 App 里塞 AI）

**三个视图的分配**：
| 阶段 | 视图 |
|---|---|
| **S1** | 今日（三块 + 打卡 + 计时）· 本周 · **时间轴**（按日分组、可写心得）· 版本号 |
| **S2** | **饼状图统计**（日/周/月）· 完成率 · 连续天数 · 验收清单打勾 |
| **S3** | 通知自愈 · 周日复盘卡片 · **周数据回传** · 周总结 |

### 5.4 数据怎么反馈给我（关键设计）
红线是"App 只读不写 vault"，所以设计为**一键复制**：

```
App 复盘页 → 生成结构化文本（本周各科时长 / 完成率 / 未完成项 / 心得）
   ↓ 你点「复制」（或「分享」）
你粘进对话给我
   ↓ 我解析
我写进 vault：周报（20 领域/个人成长/周报-YYYY-Www.md）+ 更新学习状态-共同.md + 按需调下周计划
```
- 备选：导出 `.json`（分享到微信/文件）；或直接生成一段 Markdown 供粘贴
- **为什么不自动写回**：自动写回需要 App 持写权限并处理冲突（两台设备就乱），违背"只读"与"个人工具"的简洁性；一键复制只多一次粘贴

### 5.5 需要豆包给建议吗——**不需要**
理由：这批需求是**数据结构 + 交互实现**问题，不是文案调性/内容视角问题（豆包的强项在后一类）；引入外部意见只会多一轮返工。若我需要外部输入（如界面中文措辞的取舍），会**明确指名**要什么。
